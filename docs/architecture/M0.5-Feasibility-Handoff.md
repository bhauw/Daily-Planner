## Conclusion and scaffold authorization

The official Codex transport and deterministic OAuth safety design are feasible. The approved local-v1 distribution specification authorizes M1 implementation planning, but this handoff still does **not** authorize live capabilities or provider/vault writes. The exact-folder picker and both signed persisted-bookmark relaunch gates now pass, while these gates remain unresolved:

1. live Google read-only authorization, refresh, three read-only calls, revocation, and cleanup (`BLOCKED_BY_USER_AUTH`);
2. locked-state readability for the proposed resident-access Keychain class (`BLOCKED_BY_USER_ACTION`) before any locked scheduling claim;
3. review and execution handoff for the separate [M1 implementation plan](../superpowers/plans/2026-08-30-daily-planner-m1-read-only-shell.md).

The failed helper/IPC gate remains accurate evidence, but the project owner has chosen not to make it a local-v1 prerequisite. The approved local-v1 design accepts an unsandboxed personal app with explicit compensating controls and defers a sandboxed-main-app/helper boundary to v2. It is now the planning authority for the separate M1 plan.

The sandboxed no-panel bookmark and direct-Codex results are explicit `FAIL` observations. They prevent treating a sandbox/helper distribution as proven, but they do not establish why either operation failed. The accepted personal local-v1 tradeoff does not convert them to passes. The project must not widen entitlements, claim locked scheduling, access live Google data, or access the real vault to force a pass.

## Observed behavior versus recommendations

Observed behavior is limited to the gate table and committed sanitized evidence. The architecture below is either a binding contract supported by passed evidence and the approved product brief, or a clearly marked conditional recommendation. No recommendation upgrades a failed or blocked gate.

## Architecture and dependency direction

The production scaffold should preserve these boundaries:

```text
DailyPlannerApp / UI / onboarding
              |
              v
Application workflows (sync, prioritize, propose, approve, execute, reconcile)
              |
              v
Domain contracts (SourceItem, ActionBundle, ApprovalRecord, AssistantJob,
                  state machine, privacy/retention policies)
              ^
              |
Infrastructure adapters (Google, Codex App Server, encrypted store,
                         Keychain, vault, scheduler, notifications)
```

- Domain code imports no UI, Google, Codex, SwiftData, Security, or filesystem implementation.
- Application workflows depend on domain protocols. Adapters implement those protocols and are injected.
- Only deterministic application code may execute typed actions. Codex receives no Google/Vault write tools and cannot approve actions.
- A global dry-run/no-external-write interlock wraps every Google and vault write adapter in M1.
- Candidate packages/targets: `DailyPlannerDomain`, `DailyPlannerApplication`, `DailyPlannerPersistence`, `GoogleAdapter`, `CodexAdapter`, `VaultAdapter`, `MacPlatform`, and the SwiftUI app target. Fake adapters live in test-support targets.

## Architecture rulings

### R1 — Codex transport: select version-pinned App Server v2 over stdio

- **Ruling:** Use one supervised `codex app-server --stdio` client for persistent assistant sessions and typed queued assistant jobs. Generate and pin the installed stable v2 JSON schema; validate every envelope, request ID, thread/turn ID, terminal state, and output schema. Start with `approvalPolicy: never`, no dynamic tools, and the least-capable sandbox/cwd contract the pinned schema supports.
- **Evidence:** The live synthetic turn and 18-test fault suite passed, including archive acknowledgement and termination/cleanup. [Codex evidence](evidence/codex-bridge.json).
- **Rejected alternative:** `codex exec --ephemeral --output-schema` is not selected for v1 because it was not proven in this spike and does not satisfy the persistent contextual assistant requirement by itself. AXON's bridge is prohibited.
- **Reversibility:** `AssistantClient` is a port; a later isolated-job adapter can be added without changing domain schemas.
- **Cost if wrong:** Replacing the transport requires adapter/protocol migration and queue replay compatibility, not changes to approval or provider execution rules.
- **Operational constraint:** Run the Codex subprocess test suite serially and never alongside other Swift builds. The identical 18-test `--no-parallel` suite hung under three-way build contention and then passed alone, 18/18 in 4.727 seconds. Treat this as build orchestration evidence, not a code defect or a reason to weaken deadlines.
- **Production hardening from deferred minor:** Raw stderr must never be persisted. Reduce failures to a finite allowlist plus bounded counters; apply a deny-by-default path/credential scrub before any optional diagnostic retention. The probe redactor covers its cwd, the home path, common absolute paths, and common token forms, but does not prove exhaustive secret/path redaction.

### R2 — Distribution/sandbox: approved personal local-v1 decision

- **Ruling:** Use one local, non-App-Store, unsandboxed native app for the personal v1. Launch the fixed validated Codex executable directly, keep Google credentials in exact Keychain items, and expose vault access only after explicit folder selection. The complete compensating controls and limitations are in the approved [local-v1 distribution design](../superpowers/specs/2026-08-30-daily-planner-local-v1-distribution-design.md).
- **Evidence:** Both signed user-selected bookmark save/relaunch flows passed. Unsandboxed automated access and direct Codex launch passed. Sandboxed no-panel bookmark save and direct Codex launch still failed without a proven cause. [Security evidence](evidence/security-boundary.json).
- **Deferred alternative:** A sandboxed main app plus separately installed helper requires a new v2 feasibility design and signed end-to-end proof. The rejected helper/server draft is not an implementation plan.
- **Reversibility:** Vault, Codex, Google, and persistence remain behind separate ports so a later distribution boundary can change without rewriting domain approval semantics.
- **Cost if wrong:** The v1 process has broader filesystem, subprocess, and network reach than its application policies. A later sandbox/helper migration requires signing, installation, IPC, lifecycle, bookmark, credential, update, and support work.
- **Review gate:** The committed design is approved and the separate M1 implementation plan is written. Implementation begins only through the selected reviewed-plan execution workflow; live Google, vault-content access, and provider writes remain separately gated.

### R3 — Keychain accessibility: provisional pending the locked-state run

- **Ruling:** Do not bind production OAuth tokens, home base, or envelope keys to an accessibility class yet. The candidate for resident post-login scans is `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`; `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` remains the more restrictive fallback if background work while locked is not required.
- **Evidence:** Synthetic unlocked round trips passed. Actual locked readability is `BLOCKED_BY_USER_ACTION`; the OAuth probe's `WhenUnlockedThisDeviceOnly` boundary was verified with a recording backend, not a live locked Mac. [Security evidence](evidence/security-boundary.json).
- **Rejected alternative:** Do not claim `AfterFirstUnlockThisDeviceOnly` locked behavior from an unlocked round trip, and do not default to always-accessible/deprecated classes.
- **Reversibility:** Version Keychain records and migrate by rewrapping local envelope keys; OAuth tokens can be replaced by reauthorization.
- **Cost if wrong:** Too restrictive stops locked resident scans; too permissive increases the post-unlock exposure window. Key loss or failed rotation must wipe encrypted cache content and rebuild from Google.
- **Platform note:** On macOS, the selected accessibility attribute must use the data-protection Keychain as required by [Apple's Keychain attribute documentation](https://developer.apple.com/documentation/security/ksecattraccessible).

### R4 — Vault access and writing: bookmark feasibility proven; future access remains conditional on explicit user folder selection

- **Ruling:** Use an explicit user-selected security-scoped folder bookmark. Resolve staleness, call balanced start/stop access, reject symlink/path-traversal escapes, coordinate reads/writes with `NSFileCoordinator`, and atomically replace only the stable managed daily-summary marker block. Never touch `.obsidian/`.
- **Evidence:** The unsandboxed fake-vault save/resolve/move/stale path and process-boundary model passed. Both signed variants also passed exact user-selected save and fresh-process resolve/read. Apple's documented bookmark lifecycle and file coordination support the mechanism: [macOS App Sandbox file access](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox).
- **Rejected alternative:** No hard-coded path, broad home-directory access, uncoordinated overwrite, append-on-retry, or real-vault canary.
- **Reversibility:** The bookmark can be discarded and reselected; the vault adapter owns path and coordination details.
- **Cost if wrong:** Failed access loses summaries/context; an unsafe writer risks user-note corruption, duplicate blocks, or data exposure.
- **Deferred cleanup minor disposition:** The interactive bookmark is outside the runner-owned directory so it can survive between the two signed processes by design. The fixed runner's `EXIT`, `INT`, `TERM`, and `HUP` trap invokes each variant's exact cleanup mode and deletes the exact bookmark; final hygiene also scans for both exact filenames. This closes ordinary interruption cleanup coverage. An uncatchable process termination can still bypass shell traps, so production onboarding must clean stale temporary onboarding artifacts on next launch.

### R5 — Google OAuth publishing and scopes: bind offline design; keep live capability blocked

- **Ruling:** Use a Desktop OAuth client, system browser, exact IPv4 loopback callback on an ephemeral port, PKCE S256, random state, and full-set reauthorization. Development uses External/Testing with the owner as a test user. Personal steady state targets External/In production under the applicable Google policy; this handoff does not claim verification or production eligibility.
- **Evidence:** All deterministic safety checks passed; live consent/refresh/API behavior remains `BLOCKED_BY_USER_AUTH`. [Google evidence](evidence/google-oauth.json). Google documents loopback as the recommended desktop mechanism and states installed apps do not support incremental authorization: [OAuth for desktop apps](https://developers.google.com/identity/protocols/oauth2/native-app). Testing has tester and refresh-token limitations: [sensitive-scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification).
- **Identity set (binding and tested offline):** `openid`, `email`.
- **Read-only set (binding and tested offline):** identity plus `https://www.googleapis.com/auth/gmail.readonly`, `https://www.googleapis.com/auth/calendar.readonly`, and `https://www.googleapis.com/auth/tasks.readonly`.
- **Write-enabled target (exact provisional set; not authorized or canary-proven):** `openid`, `email`, `https://www.googleapis.com/auth/gmail.modify`, `https://www.googleapis.com/auth/calendar.readonly`, `https://www.googleapis.com/auth/calendar.events`, and `https://www.googleapis.com/auth/tasks`. `gmail.modify` supports the required read/compose/send/label-state behavior without permanent-delete authority; `calendar.readonly` retains Calendar-list/mapping reads while `calendar.events` limits writes to events. Google documents the scope capabilities in [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes) and [Calendar scopes](https://developers.google.com/workspace/calendar/api/auth). This complete set must replace—not incrementally extend—the read-only grant and must be re-reviewed immediately before the M4 canary.
- **Calendar-label exception:** Prefer user-preprovisioned event labels and the event-only write scope. If current API validation proves label administration requires broader Calendar authority, that exact replacement set is a separate onboarding bundle/security ruling; it is not authorized here.
- **Rejected alternative:** No incremental scope accumulation, embedded web view, copied authorization code, checked-in client identifier, service account, or write scope during read-only milestones.
- **Reversibility:** OAuth capability sets are versioned; downgrade revokes the grant and reauthorizes the lower set.
- **Cost if wrong:** Scope changes force consent again; Testing tokens can expire; broader/restricted scopes can trigger verification or policy work. The app must disable unsupported capabilities rather than silently widening scopes.
- **Deferred readiness minor:** `LoopbackCallbackListener` protects terminal completion but its readiness callback is not one-shot across a theoretical ready-then-failed transition. Before a live milestone, add a one-shot readiness gate so the browser/open/request construction path cannot run twice. This does not upgrade or downgrade the unattempted live gate.

### R6 — Resident scheduler promise: bind a bounded promise, not 24×7 service

- **Ruling:** Use a resident menu-bar app, `SMAppService` launch-at-login registration, persisted 6 AM/noon/9 PM slots in `America/Vancouver`, one consolidated catch-up after wake/relaunch, last-success/residency UI, and duplicate-instance suppression. Promise ±15 minutes only while the resident app is awake.
- **Evidence:** This is the approved product contract, not a completed M0.5 runtime probe. Apple exposes login/background service registration and observable status through [SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice).
- **Rejected alternative:** No claim of exact wall-clock execution, automatic restart after explicit Quit/crash, operation while the Mac is off, or 24×7 cloud service.
- **Reversibility:** The scheduler is an injected clock/slot service; a future launch agent or cloud engine can replace it in v2 after a new review.
- **Cost if wrong:** Missed scans or duplicate catch-ups can produce stale priorities and duplicated jobs. M6 must pass sleep, DST, disabled-login-item, crash, and seven-day stability tests.

## Persistence, schemas, and migrations

- SwiftData stores non-content metadata and encrypted envelopes only. Envelope header fields include algorithm, key version, nonce, ciphertext, and authentication tag; nonces are unique per record.
- Start explicit schema versions at `ActionBundle.v1`, `AssistantJob.v1`, `ApprovalRecord.v1`, and `EncryptedEnvelope.v1`. `ApprovalRecord.v1` owns the complete canonical review manifest, its hash, provider/source tokens, warnings, actor, and timestamp; there is no separate `ApprovalManifest` authorization schema. Unknown/newer versions fail closed and remain non-executable.
- Migration stages are decode old -> validate -> transform in memory -> encrypt/write new -> verify -> remove old. Never log plaintext migration failures.
- Durable outbox and transaction journal writes precede provider calls. A crash resumes with reconciliation, never an assumed retry.
- Key loss or failed rotation wipes content cache and derived indexes, preserves only safe configuration/receipts that remain usable, and rebuilds Google-sourced data after reauthorization.
- [Field-level lifecycle requirements](data-lifecycle-matrix.md) and [action/reconciliation requirements](action-state-machine.md) are binding inputs to M1.

## Threat-model requirements carried into M1+

| Threat | Required control and test seam |
|---|---|
| Prompt injection / context exfiltration | Treat email, attachment, and vault content as quoted untrusted data; no model write tools; typed output allowlist; outbound context manifest and DLP check; adversarial fixtures |
| Recipient/attendee/attachment mutation | Canonical manifest includes exact normalized recipients, reply-all, attendees, attachment digests, target, and disclosure; any mutation invalidates approval |
| Attachment attack | Signature validation, macro/executable rejection, parser isolation, hard size/time/memory/decompression/OCR limits, password-protected status, verified temp cleanup |
| OAuth loss/revocation/account mismatch | Exact account binding, typed failure, pause writes, reconnect UI, revoke/clear unusable grant, retain encrypted queue |
| Key loss/rotation failure | Fail closed, wipe encrypted cache, rebuild from Google, never retain plaintext fallback |
| Crash or timeout after possible commit | Durable attempt journal, `unknownOutcome`, provider reconciliation before retry/compensation |
| Stale/concurrent source or interval | Bind provider tokens and Calendar interval snapshot into approval; refresh at preflight; invalidate affected approval on change |
| Vault path/conflict attack | Security-scoped root, standardized/real-path containment, symlink rejection, coordination, atomic marker-block replace, conflict/retry journal |
| Sensitive diagnostics | Finite allowlisted events/counters; no source text, IDs that disclose content, paths, headers, credentials, prompts, or model transcript |

## Provider constraints validated for later milestones

- Gmail reconciliation uses `messages.list` with Sent/search constraints and the deterministic RFC `Message-ID`; Gmail documents API filtering and the `rfc822msgid` operator: [Gmail API filtering](https://developers.google.com/workspace/gmail/api/guides/filtering), [Gmail search operators](https://support.google.com/mail/answer/7190).
- Calendar create supplies an API-valid deterministic event ID. Google documents that a client-supplied ID prevents duplicates after an ambiguous failure: [create events](https://developers.google.com/workspace/calendar/api/guides/create-events). Updates/deletes use `etag`/`If-Match`: [resource versions](https://developers.google.com/workspace/calendar/api/guides/version-resources).
- Tasks has no client-supplied create ID. Store a stable opaque operation marker in `notes`, search/reconcile before retry, and use `etag` on mutation. The API stores due dates only and discards time: [Tasks resource](https://developers.google.com/workspace/tasks/reference/rest/v1/tasks).
- Calendar attendee notifications are controlled by `sendUpdates` and are consequential writes; cancellation is not silent Undo.
- Calendar labels remain an onboarding mapping with icon/text fallback. Event label writes and any required scope widening must be verified against the API version before M4.
- MapKit provides local machine-readable place/ETA work; no-key Google Maps URLs are human-facing handoff only. No paid Maps route dependency is introduced.
